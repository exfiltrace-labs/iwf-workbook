## Background

Once memory has been preserved and the encryption picture is settled, the next step in a live acquisition is the disk. The image you produce here is the bedrock evidence for everything that follows. File recovery, registry analysis, timeline reconstruction, and every analytical question you'll ever ask about this system will be answered against this image, not against the live machine. The discipline is to produce an image that is provably a bit-for-bit copy of the source, hashed and verified, with case metadata that travels along with the raw bytes.

In this lab you'll prepare a small source disk on your workstation, image it with **FTK Imager**<Cite id="ftk-imager" />, verify the image's integrity, and write the kind of acquisition record a real engagement requires.

## Objectives

By the end of this lab you should be able to:

- Create a forensic image of a live volume using FTK Imager.
- Choose an appropriate image format and understand the trade-offs.
- Verify image integrity through hash comparison.
- Document an acquisition with the level of detail a real engagement requires.

## Setup: Prepare a source disk

In a real engagement the source disk would be the suspect's. For this lab, capturing an image of your VM's main disk would take a long time and use up most of the free space on the host. Instead, you'll mount a small NTFS volume backed by a virtual hard disk file (a `.vhdx`<Cite id="vhdx" />), populate it with a handful of sample files, and image that.

From an **elevated** PowerShell session, drop the execution policy and run the `prep.ps1` script from the `Exercises` directory:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
C:\Forensics\Exercises\iwf\Disk_Imaging\prep.ps1
```

The script creates a 500 MB virtual hard disk file, attaches it as drive `F:`, formats it NTFS with the label `Source`, and writes a small folder tree under `Documents\`, `Downloads\`, and `Pictures\`. When it finishes, it prints a summary line with the mount point, the VHDX path, and a file count.

## Step 1: Locate FTK Imager

On a real engagement, you'd introduce your acquisition tools into the environment from outside the suspect machine. The typical approach is a clean, prepared external drive that holds your portable acquisition tools and enough free space to hold the output image. You connect the drive to the suspect, run the tool from the drive, and write the output back to the drive.

For the sake of this lab, you'll skip the external drive and run FTK Imager straight from the same VM you're imaging.

First, we need to install **FTK Imager**<Cite id="ftk-imager" />. The installer is staged in the tools folder under `C:\Forensics\Tools\FTKImager\`. Confirm it's there:

```powershell
Get-ChildItem 'C:\Forensics\Tools\FTKImager\'
```

You should see an `Exterro_FTK_Imager_(x64)-*.exe` file. Make a note of its full path - you'll run it in the next step. If it's missing, you can grab the installer directly from [Exterro's FTK Imager page](https://www.exterro.com/digital-forensics-software/ftk-imager).

FTK Imager is a free, GUI-based disk-imaging tool from Exterro (originally AccessData) that produces forensic images in multiple formats. Whether that GUI footprint matters depends on the acquisition type. In a traditional **dead acquisition** scenario, the drive is write-blocked and read on your examiner's workstation, so the imaging tool's footprint lands on your box, not the suspect's. A feature-rich GUI like FTK Imager is the natural choice.

In a **live acquisition** scenario, the tool runs on the suspect itself, typically because encryption forces a live logical image. The same footprint pressure that pushes memory acquisition toward small CLI tools still applies, though less acutely since the volatile evidence is already captured. Smaller CLI alternatives like `dc3dd` or `ewfacquire` are worth considering when footprint matters.

<Callout type="warning" title="Note">
  In this lab you image a volume on the same Windows machine you are sitting at and write the output image to that machine's local disk. On a real engagement, you'd want the imaging tool and the captured image to live on external media. We are taking the shortcut here for the sake of demonstration and reproducibility.
</Callout>

## Step 4: Launch FTK Imager and start the image wizard

Right-click `C:\Forensics\Tools\FTK Imager\FTK Imager.exe` and choose **Run as administrator**.

Open **Help → About FTK Imager** and read off the version number. Record it under `Tool version:` in `case_notes.txt`.

<Figure
  src={ftkVersion}
  alt="About FTK Imager dialog showing Exterro FTK Imager version 4.7.3.81 with Copyright 2024 Exterro and License Agreement, Acknowledgements, and OK buttons"
  caption="The About FTK Imager dialog. Record the version string under Tool version in your case notes."
  width={450}
/>

From the main window choose **File → Create Disk Image**. A dialog opens asking what kind of source you want to image:

<Figure
  src={selectSource}
  alt="FTK Imager Select Source dialog with radio buttons for Physical Drive, Logical Drive (selected and outlined in red), Image File, Contents of a Folder, and Fernico Device, plus Back/Next/Cancel/Help buttons"
  caption="FTK Imager's Select Source dialog. The source-type choice determines what kind of evidence FTK Imager will read from."
  width={600}
/>

The choices are:

- **Physical Drive** captures the entire raw block device, including partition tables and unallocated space between partitions. This is what you use when you want the most faithful representation of the suspect's disk.
- **Logical Drive** captures a single mounted volume. You get the file system and everything inside it (including unallocated space within the volume), but not other partitions on the same physical disk and not the partition table.
- **Image File** re-images an existing image, useful for format conversion or sub-imaging.
- **Contents of a Folder** is a file-level acquisition that produces a logical evidence file, not a volume image.
- **Fernico Device** is for the Fernico FAR system, a specialized backup-tape style appliance.

For this lab you're imaging the `F:` volume, so choose **Logical Drive** and click **Next**. Pick `F:\ [Source]` from the dropdown and click **Finish**. FTK Imager confirms the source on the next screen.

<Callout type="tip" title="Encrypted systems: prefer Logical Drive">
  When you're imaging an encrypted system, it's generally recommended to go with a **live logical image** wherever possible. A logical image reads through the operating system's decrypted view while the keys are still in RAM, so what lands on your evidence drive is data you can actually analyze.
</Callout>

## Step 5: Configure the destination

In the next window, FTK Imager presents the Create Image dialog with your selected source listed at the top and an empty Image Destination(s) list below it. Click **Add** to add an image destination. The format dialog appears.

<Figure
  src={imageType}
  alt="Left: FTK Imager Create Image dialog with the F:\ source listed, an empty Image Destination(s) list, and the Add button highlighted. Right: Select Image Type dialog with Raw (dd), SMART, E01 (selected and outlined in red), and AFF radio buttons."
  caption="Clicking Add in the Create Image dialog opens the Select Image Type dialog. Choose E01, the standard forensic format that embeds case metadata and computes integrity hashes inline."
  width={900}
/>

Choose **E01** and click **Next**. The case metadata screen appears. Fill in the optional but important information:

- **Case Number**: `LAB-9-3-001` (or whatever identifier you're using)
- **Evidence Number**: `EV-001`
- **Unique Description**: `Lab acquisition - prepared source disk`
- **Examiner**: Your Name
- **Notes**: `Imaging the prepared F: volume`

The **E01** format is the preferred pick over a raw `dd` image in most cases, because it embeds case metadata, supports compression and segmenting, and computes integrity hashes inline. This metadata gets embedded inside the resulting E01 file and travels with the image forever. Anyone who opens it in any EWF<Cite id="ewf" />-aware tool later will see these fields.

Click **Next** to reach the destination screen and fill it in:

- **Image Destination Folder**: `C:\Forensics\Exercises\iwf\Disk_Imaging\image` (make a new sub-folder)
- **Image Filename**: `EV-001`
- **Image Fragment Size (MB)**: leave at the default `1500`. This controls how large each `.E01` segment is before the image spills into `.E02`, `.E03`, and so on. A 500 MB source easily fits in a single segment.
- **Compression**: leave at the default `6`. Higher compression saves disk space at the cost of acquisition speed.
- **Use AD Encryption**: leave unchecked.

Click **Finish**. You'll be back on the main Create Image dialog with the destination listed.

## Step 6: Starting the acquisition

Before you click **Start**, confirm two checkboxes at the bottom of the Create Image dialog:

- **Verify images after they are created** - this triggers the very important post-acquisition hash comparison.
- **Precalculate Progress Statistics** - optional, gives you an ETA during acquisition.

<Figure
  src={verifyResults}
  alt="FTK Imager Create Image dialog with the F:\ source listed, the EV-001 [E01] destination path filled in, Verify images after they are created checked, and the Start button highlighted in red"
  caption="The Create Image dialog right before clicking Start. The destination is set, Verify images after they are created is checked, and Start is ready to go."
  width={500}
/>

Click **Start**. A progress window appears showing source size, elapsed time, estimated time remaining, and current operation. For a 500 MB source on a local SSD the acquisition phase finishes in well under a minute. FTK Imager then automatically moves into the verification phase, re-reads the image it just wrote, recomputes its hashes, and compares them against the hashes it computed from the source during the write.

Don't touch the system while it runs. When acquisition finishes and verification begins, FTK Imager will print "Verifying" in the progress dialog. Wait for it to complete before moving on.

## Step 7: Verify the hashes

When verification completes, a results window will appear with the resulting stored and computed hash values, integrity checks, and a verdict:

<Figure
  src={hashVerify}
  alt="Left: FTK Imager Creating Image dialog showing Status 'Image created successfully' with the Image Summary button highlighted. Right: Drive/Image Verify Results dialog showing MD5 and SHA1 sections with matching Computed, Stored verification, and Report hashes, Verify result reading Match for both, and no bad blocks found in the image."
  caption="Left: the Creating Image dialog reports Image created successfully. Right: the Drive/Image Verify Results dialog shows the MD5 and SHA1 hashes lining up exactly, with Verify result reading Match for both algorithms."
  width={900}
/>

FTK Imager computes both **MD5** and **SHA-1** for an E01 acquisition by default. Each algorithm has its own section in the dialog with three values: the **Computed hash** (over the bytes read from the source during the write), the **Stored verification hash** (the value baked into the E01), and the **Report hash** (over the bytes read back from the image during the verification pass). All three should match, and the **Verify result** row at the bottom of each section confirms it with a `Match`. That means the bytes that were written to the E01 are bit-identical to the bytes that were read from the source.

Before closing the Creating Image dialog, click **Image Summary...** to see the full acquisition report. This report contains the case metadata, source geometry, MD5 and SHA-1 hashes, acquisition and verification timestamps, and the verification verdict. A copy of the same report is also written next to the E01 as a `.txt` file with the same base name (`EV-001.txt`), so the record is preserved on disk even if you close the dialog.

Copy both hash values into `case_notes.txt` under `Image MD5:` and `Image SHA-1:`. Record the end time under `End time:` from your reference clock and compute the duration.

<Callout type="warning" title="A mismatch is a stop condition">
  If the source and image hashes do not match, the image is not forensically sound. The correct response is to **stop**, document the mismatch (which hashes, which values, what FTK Imager reported), investigate the cause, and re-acquire. Do not analyze a mismatched image (but hold onto it for documentation and failure analysis).
</Callout>

## Step 8: Mount the image and confirm content

A hash match means the image is a faithful copy of what FTK Imager read off the source. It's still worth opening the image to confirm you imaged the right thing. In the FTK Imager main window choose **File → Add Evidence Item**, choose **Image File**, and browse to `C:\Forensics\Exercises\iwf\Disk_Imaging\image\EV-001.E01`. Click **Finish**.

The left-hand Evidence Tree now shows the image as a new root. Expand it to find the `Source` volume, then drill into `Documents\`, `Downloads\`, and `Pictures\`. You should see the same sample files the prep script wrote. Click one of them to see its content rendered in the preview pane.

## Wrapping Up

You just produced a verified forensic image: a hash-matched, metadata-embedded E01 of a known source, with an acquisition record that names the case, the examiner, the tool, the source, the destination, the hashes, the times, and the verification result. Every real disk acquisition follows the same workflow you just walked through. Real cases have bigger sources and longer runtimes, but the underlying workflow remains consistent.

FTK Imager isn't the only tool that does this. **X-Ways Forensics**, **Belkasoft Acquisition Tool**, and **Magnet ACQUIRE** are all examples of similar tools that produce E01 images with comparable verification. On the CLI, **dd** and **dc3dd** can produce raw images. The discipline is the same regardless of tool: read the source bit for bit, hash what you wrote, verify it matches what you read, and document the process.
