## Background

A Windows endpoint generates an enormous volume of forensic evidence simply by operating. Some of those traces come from the operating system itself recording its own work. Others are byproducts of user activity. A forensic examination of a Windows system is largely the work of finding those traces, understanding what each one proves, and assembling them into a coherent narrative.

This lab gets you oriented in where the most important traces live and what they look like when you pull them off disk. You're going to mount a KAPE triage collection of a real Windows system and walk through the major artifact categories one at a time, finding a concrete example of each. Each category maps to a kind of activity it serves as evidence of, which is why the standard mental model is called the "Evidence Of..." framework<Cite id="evidence-of" />.

## Objectives

By the end of this lab you should be able to:

- Mount a KAPE triage VHDX of a Windows system on the analyst workstation.
- Determine the source system's Windows version from the collected `SOFTWARE` registry hive.
- Locate and identify Prefetch files as evidence of program execution.
- Locate and identify LNK files in `Recent\` as evidence of file/folder opening.
- Locate Recycle Bin `$I` / `$R` pairs as evidence of deleted items.
- Trace USB device history through `SYSTEM\Enum\USBSTOR` and `setupapi.dev.log`.

## Setup: Mount the image

**KAPE**<Cite id="kape" /> is the most widely-used DFIR triage tool in the industry, written by Eric Zimmerman and maintained by Kroll. In modern incident response, full bit-for-bit disk images are usually a deliberate escalation, not the default. The increasingly modern approach is a **triage collection**. On a typical Windows endpoint, roughly one percent of the files hold 99 percent of what an investigator looks for. Triage collection targets that one percent directly, so you get usable evidence in the time it would take a full disk image to barely start copying. 

KAPE reads in a defined list of forensically-relevant paths (targets) and copies the matching files into a portable container, preserving original timestamps, NTFS metadata, and alternate data streams. The result is small enough to ship over the network in minutes, fast enough to capture from a live machine without taking it offline, and sufficient to answer most artifact-level questions. 

That last property is what makes triage practical at scale. Imaging 50 endpoints in a compromise hunt is rarely feasible. Collecting a triage container from each is routine. Full disk images come into play when triage isn't enough, like recovering deleted content from unallocated space or chasing malware that hides outside the known paths.

## Windows version (Registry)

The first thing every Windows examination establishes is **what Windows we're looking at**. The version drives everything downstream, because no two Windows builds keep the same artifacts in the same places, and tools that work on one build can quietly do the wrong thing on another. That information lives in the `SOFTWARE` registry hive. The registry itself isn't a single file. It's stored on disk as a set of binary files called **hives**, each holding a different branch of the registry tree. The `SOFTWARE` hive specifically holds installed-software entries plus OS-level metadata, including the Windows version values you're about to read.

**Registry Explorer**<Cite id="zimmerman-tools" /> is Eric Zimmerman's offline hive viewer. It opens a hive file directly and exposes the same tree structure you'd see in `regedit` against a live system, without needing Windows to mount the hive first. Either run it from PowerShell or double-click `RegistryExplorer.exe` in File Explorer:

```powershell
C:\Forensics\Tools\Zimmerman\RegistryExplorer\RegistryExplorer.exe
```

In Registry Explorer: **File → Load hive** and browse to `E:\C\Windows\System32\config\SOFTWARE`. Click **Open**.

Registry Explorer will pop a **Dirty hive detected!** dialog. This is a very common occurrence when collecting Registry hives. While Windows is running, the `SOFTWARE` hive is in active use, and recent writes live in transaction log files (`SOFTWARE.LOG1`, `SOFTWARE.LOG2`) until they get merged back into the hive itself.

<Figure

  alt="Registry Explorer's 'Dirty hive detected!' modal dialog asking whether to replay transaction logs against the loaded hive"
  caption="Registry Explorer flags the SOFTWARE hive as dirty because its transaction logs have unmerged writes."

/>

KAPE captures the hive and its logs in their as-of-collection state, so the hive file on disk doesn't yet reflect those pending writes. Registry Explorer can replay the logs against the hive to produce a merged copy that reflects the latest committed state at capture time.

You'll need a place to drop the merged hive. Create an `exports\registry\` folder under the lab directory:

```powershell
New-Item -ItemType Directory -Path 'C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\registry' -Force | Out-Null
```

Then click through the prompts:

1. Click **Yes** to replay the transaction logs.
2. Click **OK** at the next prompt to begin.
3. In the file picker, select **all** of the `SOFTWARE.LOG*` files in `E:\C\Windows\System32\config\` and click **Open**.
4. When asked where to save the updated hive, point it at `C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\registry\`. Registry Explorer defaults the filename to `SOFTWARE_clean`. Accept it.
5. Registry Explorer asks whether to load the updated hive. Click **Yes**.
6. It then asks whether to also load the original dirty hive. Click **No** (you want to work from the clean version).

The clean `SOFTWARE` hive is now loaded. Navigate the tree to:

```text

```

In the right-hand pane you'll see the familiar set of values: `ProductName`, `DisplayVersion`, `CurrentBuild`, `UBR`, plus an `InstallDate` and a handful of others. Together these identify the OS down to the build and update level.

## Program execution (Prefetch)

**Prefetch** is one of Windows' most reliable "Evidence Of Program Execution"<Cite id="evidence-of" /> sources<Cite id="prefetch" />. The OS writes a small `.pf` file under `C:\Windows\Prefetch\` the first time it sees a given executable run, then updates that file on subsequent runs to track how often the program has launched and which files it touched while running. Prefetch carries plenty of caveats, as evidence-of-execution artifacts generally do, but the basic claim it makes is straightforward. Each `.pf` file in this directory is evidence that an executable by that name ran on this system, with timestamps and a run count attached.

The filename convention is `EXECUTABLE-XXXXXXXX.pf`, where the eight-character hex string is a hash of the executable's full path (and for some programs, like `svchost.exe`, the command-line arguments as well). The proprietary hash we find in `.pf` files means that `notepad.exe` running from `System32` and `notepad.exe` running from some other folder produce different Prefetch files even though the leading name is the same.

**PECmd**<Cite id="zimmerman-tools" /> is Eric Zimmerman's Prefetch parser. Point it at a single `.pf` file or at a whole directory of them and it emits parsed output as CSV, JSON, or HTML. The CSV output is what you want for triage, because each row carries the source executable, the run count, the last-eight-runs timestamps, and the lists of files and directories the prefetch record references.

You'll need a folder for the parsed output. Create one:

```powershell
New-Item -ItemType Directory -Path 'C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\prefetch' -Force | Out-Null
```

Point PECmd at the whole `Prefetch\` directory in the mounted image and write CSV output into `exports\prefetch\`:

```powershell
PECmd.exe -d 'E:\C\Windows\Prefetch\' --csv 'C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\prefetch' -q
```

PECmd processes every `.pf` file in the directory and writes **two CSVs** into `exports\prefetch\`:

- The **summary** (`<timestamp>_PECmd_Output.csv`) gives one row per Prefetch file with that executable's run count and last-eight-runs timestamps.
- The **timeline** (`<timestamp>_PECmd_Output_Timeline.csv`) expands each `.pf`'s eight timestamps into individual rows so the whole machine's execution history sorts chronologically.

## File and folder opening (LNK)

**LNK files** are Windows shortcut files. The format has been around since Windows 95 and is one of the standard "Evidence Of File Opening"<Cite id="evidence-of" /> sources on a Windows endpoint. Users create LNKs deliberately when they pin something to the Start menu or drag a shortcut onto the desktop, but Windows also creates them automatically as a side effect of opening files through Explorer, dropping each one into a per-user **Recent Items** folder. 

That automatic, user-implicit creation is what makes the LNKs in `Recent\` forensically valuable. The folder lives at:

```
C:\Users\<username>\AppData\Roaming\Microsoft\Windows\Recent\
```

In the mounted image, we'll target the `mhansen` user.

LNK files come with their own caveats. They only get created when a specific Explorer shell code path fires, which means programmatic file opens through PowerShell, scripts, or direct API calls typically skip the LNK write entirely. But the basic claim a LNK in `Recent\` makes is straightforward. The user opened a particular file or folder through Explorer at a particular time, and the shortcut record retains the original target path, the target volume's serial number, and several timestamps for both the LNK itself and the file it pointed at. 

That information survives even when the target volume is no longer attached, which is what makes LNKs so durable as evidence of file opening.

**LECmd**<Cite id="zimmerman-tools" /> is Eric Zimmerman's LNK parser. Point it at a single `.lnk` file or at a whole directory of them and it writes parsed output as CSV. Each row breaks one LNK down into the full set of fields the format carries, with the most useful columns being the original target path with drive letter, the target volume's serial number, the LNK's own MAC timestamps, and the target file's MAC timestamps.

Add a folder for the parsed output:

```powershell

```

Point LECmd at the whole `Recent\` directory in the mounted image and write CSV output into `exports\lnk\`:

```powershell
LECmd.exe -d 'E:\C\Users\mhansen\AppData\Roaming\Microsoft\Windows\Recent\' --csv 'C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\lnk' -q
```

LECmd processes every `.lnk` in the directory and writes one CSV into `exports\lnk\`, named `<timestamp>_LECmd_Output.csv`. One row per parsed LNK, every metadata field broken out as its own column.

## Deleted items (Recycle Bin)

When a user deletes a file in Explorer (without `Shift+Del`), Windows moves it into the Recycle Bin instead of removing it from disk. The bin lives at `C:\$Recycle.Bin\<SID>\` on the source system, where `<SID>` is the user's security identifier. In the mounted image, that's `E:\C\$Recycle.Bin\<SID>\`, and a multi-user system has one SID subfolder per interactive account.

Every delete produces two files in the per-user Recycle Bin folder that share a base name<Cite id="recycle-bin" />. The `$I` half carries the deletion metadata, including the original full path of the deleted file, its size in bytes, and the timestamp of the delete. The `$R` half carries the actual file bytes under a randomized filename. Recovery is a matter of reading the original filename out of the matching `$I` metadata and renaming the `$R` back to that.

Recycle Bin entries come with their own caveats. Only Explorer's Delete action (right-click → Delete, or selecting a file and pressing `Del`) routes files into the bin. `Shift+Del`, `Remove-Item`, and `del` all bypass it entirely, as does almost every programmatic deletion path. Files deleted from removable media also skip the bin by default. But within those rules, an `$I` is straightforward evidence that the user deleted a particular file at a particular time through the Explorer shell, with the file's content probably still recoverable from the matching `$R`.

**RBCmd**<Cite id="zimmerman-tools" /> is Eric Zimmerman's Recycle Bin parser. It reads the binary `$I` files and writes their metadata out as CSV. Each row gives the original full path of the deleted file, its size in bytes, and the deletion timestamp.

Add a folder for the parsed output:

```powershell

```

Point RBCmd at the whole `$Recycle.Bin\` tree in the mounted image and write CSV into `exports\recyclebin\`:

```powershell
RBCmd.exe -d 'E:\C\$Recycle.Bin\' --csv 'C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\recyclebin' -q
```

RBCmd recurses into every SID subfolder, parses every `$I` file it finds, and writes one CSV (named like `<timestamp>_RBCmd_Output.csv`) with one row per recovered deletion event.

## External device usage (USB)

Windows keeps records of every USB device that has ever attached to the system, scattered across many places on disk. Multiple registry subtrees, event logs, per-user mount history, and driver install logs all carry pieces of the story. 

This lab focuses on two of the most commonly-referenced sources. The registry's **USBSTOR** subtree (inside the `SYSTEM` hive) records the device classes and individual instances Windows currently knows about, with friendly names, descriptions, and per-property timestamps for first-installed and last-connected events. 

The `setupapi.dev.log` file<Cite id="setupapi" /> is a plain-text log under `C:\Windows\INF\` where Windows appends a verbose record every time it installs a driver, including for every USB device it has ever seen. 

USB tracking comes with many caveats, more than are worth diving into here. We'll keep this section to the high-level view.

### USBSTOR

The **USBSTOR** enumeration lives in the `SYSTEM` registry hive. Load the `SYSTEM` hive in Registry Explorer the same way you loaded `SOFTWARE` earlier: **File → Load hive** → browse to `E:\C\Windows\System32\config\SYSTEM`.

If the **Dirty hive detected!** dialog appears again, click through the same replay flow and save the merged copy to `C:\Forensics\Exercises\iwf\Artifact_Hunting\exports\registry\` as `SYSTEM_clean`.

Once the merged hive is loaded, navigate to:

```text

```

Each subkey under `USBSTOR` represents one device class (vendor + product + revision), with names that look like `Disk&Ven_SanDisk&Prod_Cruzer_Blade&Rev_1.00`.

#### USB timestamps

Open `Properties`. Inside it is a subtree with a long GUID name, `{83da6326-97a6-4088-9453-a1923f573b29}`. That GUID is fixed across every Windows install and identifies the device-install property category, so every USBSTOR device's `Properties` carries exactly the same one. Open it.

Inside the GUID node are numerically-named subkeys, each carrying a 64-bit FILETIME timestamp that Registry Explorer parses and displays as a readable date and time:

- `0064`: first-install date (the first time this device was plugged into this system)
- `0065`: first-arrival date (when the device's driver was first loaded)
- `0066`: last-arrival date (the most recent time the device was connected)
- `0067`: last-removal date (the most recent time the device was disconnected)

  caption="The 0064 subkey under the device-install GUID. Registry Explorer decodes the raw binary FILETIME to a human-readable date and time."
/>

Notice that this image doesn't have a `0067` subkey at all. The triage capture was taken while the SanDisk was still plugged into the source system, so Windows never had occasion to record a last-removal event. The other three timestamps (`0064`, `0065`, `0066`) are present because those events all happened (install, driver load, connect) before the snapshot.

### setupapi.dev.log

The `setupapi.dev.log` file lives at `C:\Windows\INF\setupapi.dev.log` on the source system, which means it's at `E:\C\Windows\INF\setupapi.dev.log` in the mounted image. It's a multi-megabyte plain-text file. Notepad opens it but is slow. Notepad++ or any modern editor handles it without issue.

A single USB device plug-in produces several `>>>  [Device Install (Hardware initiated) - ...]` markers as Windows registers the device at each layer of its bus stack. Filtering for the ones that mention `USBSTOR` catches the records relevant to removable storage. Each marker's line carries the device path (vendor, product, revision, and serial number) inline, with the install timestamp and Windows's driver-bind steps in the lines that follow.

From PowerShell, use `Select-String` to find installs that mention `USBSTOR`, with five lines of context after each hit:

```powershell
Select-String -Path 'E:\C\Windows\INF\setupapi.dev.log' -Pattern '>>>\s+\[Device Install.*USBSTOR' -Context 0,5
```

Cross-reference the device paths and timestamps you find here against the USBSTOR data above to build a complete attached-device timeline. One catch: `setupapi.dev.log` records timestamps in the **source system's local time**, while the registry's `0064` value is a **FILETIME stored in UTC**. The same install event reads as two different timestamps depending on which source you're looking at, so you have to add or subtract the source machine's UTC offset before they line up.

## Wrapping Up

You've now located a concrete example of every major Windows artifact category. The **registry baseline** identifies the system you're examining down to the build. The parsed **Prefetch files** document what executables have actually run on that system. The **LNK files** under `Recent\` capture what the user opened or interacted with, including items on drives that are no longer attached. Modern **Recycle Bin** artifacts `$I`/`$R` preserve both the deletion metadata and the original bytes of items the user sent to the bin. The **USBSTOR** registry key and the `setupapi.dev.log` file are part of the many artifacts that help reconstruct what removable devices have been plugged in and when. 

What you covered here is a non-exhaustive look at the "Evidence Of..." framework<Cite id="evidence-of" /> for Windows artifacts. Knowing where each category lives and recognizing what you're looking at when you find it matters far more than fluency with any one tool. That recognition is what this lab built. The deeper analytical work will build on that foundation.
