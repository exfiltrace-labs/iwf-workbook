## Background

Memory acquisition should be the first thing you do on any live system. The moment power is cut, everything in RAM is (generally) gone. There is no undo. Live memory on a typical workstation holds multiple gigabytes of state you cannot reconstruct from anywhere else: running processes and their command-line invocations, open network connections and the processes that own them, registry hive content that has not yet been flushed to disk, decrypted contents of files the user had open, authentication tokens, and much more. All of it is potentially case-relevant evidence that you could end up throwing away by pulling the plug before acquisition.

A modern Windows endpoint with BitLocker enabled and the user signed in has the volume encryption keys sitting in memory at that moment. If you prematurely pull the power from that system, the disk image you take afterward will be a wall of encrypted bytes that you cannot read. The proper acquisition procedure is to capture memory first, document what you did, and then move on to the disk.

In this lab you will use **WinPmem** to capture a full RAM image of a running Windows machine, hash it, write defensible case notes, and observe the forensic footprint that your actions inevitably leave behind.

## Objectives

By the end of this lab you should be able to:

- Perform a live memory acquisition on a running Windows system.
- Hash and verify a captured memory image.
- Document the acquisition with the level of detail a real engagement requires.
- Observe and explain the forensic footprint of the acquisition itself.

<Callout type="key">
  Memory acquisition is one of the few practices in forensics where the only way to preserve the evidence is to also modify the system holding it. The discipline is knowing exactly what you changed and being able to defend it later.
</Callout>

## Setup: Acquisition kit and destination

Of course in a real engagement, the suspect system does not come with memory acquisition tools installed. You bring your own. The typical approach is a clean, prepared external drive that holds all of your portable acquisition tools and has enough free space to hold the output memory image. You connect the drive to the suspect, run the tool from the drive, and write the output back to the drive. That keeps your footprint on the suspect down to the bare minimum required to read RAM.

For the sake of this lab, you are going to capture from the same Windows machine you are running on (your own forensic workstation) and write the output to its local disk. That is something you would never want to do in real practice. We are doing it here because the goal is to learn the workflow, not to reproduce the full operational setup.

<Callout type="warning" title="Note">
  In this lab you capture from the same Windows machine you are sitting at and write the output to that machine's local disk. On a real engagement, you'd want the acquisition tool and the captured image to live on external media. We are taking the shortcut here for the sake of demonstration and reproducibility.
</Callout>

First, locate WinPmem<Cite id="winpmem" /> within the tools directory:

```powershell
Get-ChildItem 'C:\Forensics\Tools\WinPmem\'
```

You should see a single executable, `winpmem_mini_x64_rc2.exe`. The rest of the lab uses that full path. If your filename differs, substitute it everywhere the path appears below.

Next, create a destination folder for the output image:

```powershell
New-Item -ItemType Directory -Path C:\Forensics\Exercises\iwf\Memory_Acquisition -Force
```

## Alternative acquisition tools and footprint considerations

WinPmem is not the only memory acquisition tool you will see in the field. **Magnet DumpIt**<Cite id="dumpit" /> is another command-line single-binary tool that takes a similar approach to WinPmem. **Magnet RAM Capture**<Cite id="magnet-ram-capture" /> and **FTK Imager**<Cite id="ftk-imager" /> are both GUI tools, with FTK Imager additionally able to capture disk images. **Belkasoft RAM Capturer**<Cite id="belkasoft" /> is another well-known GUI option commonly used in the field.

All of these will produce a valid memory image. For a **live acquisition** on a suspect system, the goal is to minimize the footprint of the acquisition tool itself. **Purpose-built single-binary acquisition tools generally have a smaller footprint than feature-rich GUI suites**, whether the purpose-built tool is CLI like WinPmem and DumpIt or minimal-UI like Belkasoft RAM Capturer. 

Feature-rich GUI forensics suites like FTK Imager tend to have a meaningfully larger footprint because the acquisition function ships alongside the rest of the suite's UI, plugins, and analysis code. When a heavy GUI tool launches, it typically needs to load the window manager bindings, rendering subsystems, font caches, theming code, and a stack of UI libraries. Each one loads more modules into the tool's address space and touches more files on disk. That matters because every module loaded into RAM overwrites a slice of the very memory you came to capture, and every file touched is another disk-side artifact you will have to account for in your notes.

A command-line tool that loads a driver, reads physical memory, writes the output, and exits has a far smaller footprint by design. We should always aim to keep our acquisition footprint as small as possible. For the rest of this lab we use WinPmem, but feel free to use any tool from the list above that you are more comfortable with. The workflow is conceptually identical regardless of which tool you pick: select an output path, kick off the capture, hash the result, and document your process.

<Callout type="warning" title="Warning">
  Memory acquisition is an event that a responder will typically only get *one opportunity* to perform. Having multiple tools provides several avenues for memory collection in case of a failure.
</Callout>

## Step 1: Pre-Acquisition Documentation

The first step in pre-acquisition documentation is to **set up your case notes**. In a real engagement those notes live in your own case journal, whether that is a case management tool, an examiner laptop, or even a paper notebook. We want to limit the amount of instrumentation we run and data we introduce to the suspect system. However, there are certain system-specific details we may want to document during the acquisition process itself, which we will cover in a moment.

For this lab, open Notepad as a stand-in for your examiner notebook. Save a new file as `C:\Forensics\Exercises\iwf\Memory_Acquisition\case_notes.txt` and record the following:

- A case identifier you make up for this lab, for example `LAB-9-1-001`.
- The examiner's name.
- The **current date and time**, recorded from an NTP-synced reference clock (your phone, your watch, or any accurate clock that is not the suspect machine).
- The tool you are about to run and its full path on the acquisition kit. In this lab that is `C:\Forensics\Tools\WinPmem\winpmem_mini_x64_rc2.exe`.
- The anticipated output path of the memory capture. In this lab that is `C:\Forensics\Exercises\iwf\Memory_Acquisition\memory.raw`.

Leave the file open. You will append to it as the acquisition progresses.

<Callout type="warning" title="Note">
  Just as we are running the acquisition tool from the suspect itself for the sake of this lab, we are also documenting our case notes on the suspect. On a real engagement, your case notes would live outside of the system you are capturing from. We are using Notepad here purely as a stand-in to keep the lab self-contained.
</Callout>

## Step 2: Capture the Memory Image

Now it's time to acquire a memory image! Like many similar tools, WinPmem needs to load a **kernel driver** to read physical RAM. That requires administrative privileges. Close any non-elevated PowerShell windows you have open and start a new one as Administrator. The window title should read **Administrator: Windows PowerShell**.

Before you run the tool, record the start time in `case_notes.txt` from your external reference clock under a `Start time:` line. If you want to capture the **suspect's** view of the time as a separate forensic artifact (clock drift, deliberate clock manipulation), feel free to do so by glancing at the taskbar clock and recording its reading alongside your external timestamp.

Now kick off the capture by invoking WinPmem with your destination path as its only argument:

```powershell
C:\Forensics\Tools\WinPmem\winpmem_mini_x64_rc2.exe C:\Forensics\Exercises\iwf\Memory_Acquisition\memory.raw
```

WinPmem will immediately load its driver, perform some setup, and begin writing the memory image. Depending on the amount of RAM the VM has, the capture typically takes a few minutes. It is common for the resulting image size to be a bit larger than the installed RAM, because the raw format pads additional hardware-reserved gaps in the address space with zeros.

<Callout type="note" title="Capture time varies wildly">
  How long the dump takes depends on how much RAM the source system has and the destination drive's write speed. A lab VM with a few GB of RAM and a local SSD may finish in only a few minutes. A workstation with 64 GB of RAM writing to a slow USB stick can take an hour or more.
</Callout>

While it runs, make sure to leave the system alone. Avoid opening new applications, browsing the web, or generating unnecessary noise. The cleaner the system state is during capture, the cleaner your resulting image will be.

When the tool finishes, read the current time off the same external reference clock you used for the start time and append it to `case_notes.txt` under an `End time:` line. Calculate the elapsed duration (end minus start) and record that too. If you want to capture the **suspect's** view of the time as a separate forensic artifact (clock drift, deliberate clock manipulation), feel free to do so by glancing at the taskbar clock and recording its reading alongside your external timestamp.

WinPmem also prints the suspect's system clock at the start and end of its run, in the form `The system time is: HH:MM:SS`. Record both values. Subtracting them gives a self-reported duration from inside the tool, on the suspect's view of time. It should agree (within seconds) with the externally-measured duration you took off your reference clock. A meaningful disagreement between the two is worth investigating before you trust the image.

## Step 3: Hash and Verify

Immediately after the capture finishes, hash the resulting memory image. This becomes your integrity baseline. Every later check that the image has not been altered should compare back to these values. There are a number of ways to compute a hash of a file, but the simplest on Windows is the built-in `Get-FileHash` PowerShell cmdlet:

```powershell
Get-FileHash -Algorithm SHA256 C:\Forensics\Exercises\iwf\Memory_Acquisition\memory.raw
```

Note that the `-Algorithm` parameter can be used to select which hash function to compute. `Get-FileHash` supports SHA-256 (the default), MD5, SHA-1, SHA-384, and SHA-512<Cite id="get-filehash" />.

<Callout type="warning" title="Be patient">
  Hashing a multi-gigabyte memory image can take several minutes to complete. `Get-FileHash` does not print progress while it works, so the terminal will sit silent and may look like nothing is happening. It's important to have patience during acquisition!
</Callout>

It is also good practice to record an MD5 hash alongside the SHA-256. SHA-256 is generally the cryptographic authority, but plenty of legacy forensic tools and case-management systems still expect an MD5 field. Recording both gives the next examiner whichever value their workflow needs without having to re-hash the image:

```powershell
Get-FileHash -Algorithm MD5 C:\Forensics\Exercises\iwf\Memory_Acquisition\memory.raw
```

And note the file size in bytes. The size becomes part of the image's identity in your case notes and acts as a quick first check that the capture is not truncated or otherwise off from what you would expect for the system's installed RAM:

```powershell
(Get-Item C:\Forensics\Exercises\iwf\Memory_Acquisition\memory.raw).Length
```

Append all three values to `case_notes.txt`. From this point forward you can verify the image's integrity at any time by re-hashing and comparing.

<Callout type="tip" title="Hash before you move it">
  Always compute the hash before copying the image anywhere else. If a copy gets corrupted in transit and you only hashed the destination, you have lost the ability to tell the difference between a bad source and a bad copy.
</Callout>

## Step 4: System Information Capture

Now that the image is captured and hashed, it is recommended to **capture detailed information about the operating system that produced it**. The OS build identifies which kernel symbols match the dump, where critical structures live in memory, and which patches were applied. 

Recording this is good practice for case documentation, even though modern memory analysis frameworks like Volatility 3 and MemProcFS can usually auto-identify the build from the dump itself. Having the build string in your case notes lets a later examiner verify that auto-detection and gives you an additional fallback.

A quick way to grab all of the relevant OS detail in one shot is the built-in `systeminfo` command. It reports hostname, OS name, OS version and build, architecture, install date, BIOS version, locale, total physical memory, and the full list of installed hotfixes. Run it from the same elevated PowerShell you used for the capture, and pipe it through `Tee-Object` so the output appears on screen and lands in a file at the same time:

```powershell
systeminfo | Tee-Object -FilePath C:\Forensics\Exercises\iwf\Memory_Acquisition\systeminfo.txt
```

That file now sits alongside your case notes and the memory image. Copy the hostname, OS name, OS version, OS build, and time zone lines out of the output and into `case_notes.txt`. You or another analyst can refer to the full `systeminfo.txt` later without re-running anything on a system that may by then no longer exist.

## Step 5: Observe the Footprint

Memory acquisition is one of the few practices in forensics where the only way to preserve the evidence is to also modify the system holding it. The footprint your tool leaves behind is unavoidable, but it is also predictable, finite, and defensible if you understand what it consists of.

WinPmem itself prints the most important parts of its footprint in its own output. When you ran the capture, you would have seen output like:

```
WinPmem64
Extracting driver to C:\Users\<user>\AppData\Local\Temp\<random>.tmp
Driver Unloaded.
Loaded Driver C:\Users\<user>\AppData\Local\Temp\<random>.tmp.
Deleting C:\Users\<user>\AppData\Local\Temp\<random>.tmp
```

And when it finished:

```
Driver Unloaded.
```

Each of those lines is a discrete, attributable artifact on the suspect. For example:

- The `.tmp` file in `%TEMP%` is the kernel driver binary WinPmem dropped on disk. WinPmem deletes the on-disk copy almost immediately after loading it into the kernel (you can see this in the `Deleting...` line), but the create and the delete each record a USN Journal entry and leave a freed `$MFT` record carrying the original timestamps.
- `Loaded Driver` is the moment a kernel-mode driver entered the running kernel under your administrator credentials. The driver load is observable to kernel-mode callbacks and is exactly the kind of event an EDR product would surface and attribute back to your session.

The rest of the footprint is not announced in the output but follows from running the tool:

- Reading physical memory exercises kernel caches and page tables.
- Writing the multi-gigabyte output file generates NTFS metadata activity.
- Had you been working from external USB media (the way you would on a real case), connecting that drive would have written additional records under `HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR`, the `SetupAPI` device logs, the Windows event logs, and elsewhere.

None of that is malicious or improper. It is the unavoidable footprint of doing the job. This is why we document the acquisition times so carefully. They let us explain on record when the collection activity was performed, and let a future examiner match the artifacts left behind to that recorded window. The discipline is to know what you did, document what you did, and be able to explain it down the road, if asked.

## Step 6: Final Documentation

Open your `case_notes.txt` and confirm it has all of the following recorded:

- Case identifier
- Examiner
- Tool name and full path
- Output path
- Start timestamp, end timestamp, and elapsed duration (from both the suspect system and a trusted reference clock).
- SHA-256 hash
- MD5 hash
- File size in bytes
- Source system hostname, version, build, and time zone

That file is your case style documentation for this acquisition. In a real case, this is the level of detail you want in your evidence log and your chain of custody record.

## Wrapping Up

Congrats! You just performed a real memory acquisition. You captured a multi-gigabyte snapshot of everything that was in RAM at the moment you ran the tool. You hashed it for integrity. You documented the tool, version, timestamps, file size, and hash values. And you observed the unavoidable forensic footprint of the acquisition itself.

Now that the most volatile of evidence has been *preserved* and *collected*, it can safely be *analyzed*. Memory analysis is its own discipline. Tools like the Volatility Framework<Cite id="volatility" /> or MemProcFS<Cite id="memprocfs" /> are where the analysis portion of the workflow lives. What you have here is the front end of the workflow. The ability to capture cleanly, hash, and document.
